# In-Browser LLM Exploration

**Date:** 2026-10-20
**Branch:** `explore/in-browser-llm`
**Status:** Research complete, no code yet. The next step is the spike below.

**Goal:** a chat inside the knowledge-vault editor, powered by a small LLM that runs entirely in the browser. It answers questions about the vault and issues reactor and vault commands (actions).

## Do we need to fine-tune for command generation?

**Not yet.** Start with the stock model. Narrow the candidate operations with retrieval, then constrain the output to the chosen operation's schema. Fine-tune only if an eval says it's needed.

- Published tool-calling scores at 350M are low. LFM2.5-350M scores 35–63% out of the box and 96–98% after LoRA ([Distil Labs](https://www.distillabs.ai/blog/fine-tuning-liquids-lfm25-accurate-tool-calling-at-350m-parameters/)). All of those numbers come from unconstrained decoding, though. Most failures at this size are structural (free text, invented function names, malformed JSON), and constrained decoding removes them.
- What constraints can't fix: picking the wrong operation, getting argument values wrong, or emitting one action when two were needed.
- We have 102 operations across 12 models, roughly 6–12k tokens of schema. Small models choose much worse from long tool lists, so retrieve 5–10 candidates first.
- **Fine-tune if** the model picks the right operation less than about 90–95% of the time when that operation was among the retrieved candidates, or if argument errors stay above our tolerance.
- The eval set (utterance → action pairs generated by a large teacher model from the schemas) doubles as the LoRA training set, so trying without a fine-tune first costs almost nothing extra. A fine-tune would need thousands of examples. Tooling: leap-finetune, Unsloth or TRL, then merge, convert to GGUF and quantize to Q8_0.

## Proposed architecture

1. **Runtime:** wllama 3.8.1 in a web worker, running `LiquidAI/LFM2.5-350M-GGUF` Q4_K_M (229 MB, cached in OPFS). WebGPU is the main path, with CPU WASM as the fallback. transformers.js v4 with `LFM2.5-350M-ONNX` is the backup option. WebLLM has no LFM2 support.
2. **Command generation:**
   1. Retrieve the top-k operations from their descriptions.
   2. Constrain the operation name to that set.
   3. Fill the chosen operation's arguments under its JSON Schema. The schemas can be built from the generated Zod validators in `v1/gen/schema/zod.ts`.
   4. Restrict reference ids (`noteId` and similar) to an enum of ids that retrieval returned.
3. **The model emits only `{op, semantic fields}`.** The app builds the `{type, input, scope}` envelope and supplies `id`/OIDs and timestamps. This also fits the repo's reducer-purity rule: ids and dates come from the action input, never from the model or the reducer.
4. **Q&A stays unconstrained.** Forcing JSON measurably hurts reasoning. Answers come from retrieved notes, not from the model's own knowledge. Liquid says LFM2.5-350M is not meant for knowledge-heavy tasks (MMLU-Pro about 20).
5. **UI:** a new `chat` entry in the `ViewMode` union and `TABS` in `editors/knowledge-vault/components/DriveExplorer.tsx`. Dispatch through `dispatchActions([...], docId)` from reactor-browser.

## Scope decision: how "fully in-browser"?

| Scope | Commands | Knowledge Q&A | Needs |
|---|---|---|---|
| **A: browser LLM, server retrieval** | in-browser | `knowledgeGraphSemanticSearch` on Switchboard | nothing new server-side |
| **B: fully offline** | in-browser | in-browser index | browser embedder plus vector index (Orama, PGlite+pgvector, or brute-force cosine as in the processor) |

Command retrieval over 102 operations can be fully in-browser in both scopes. Even keyword or BM25 search may be enough at that size.

### Why the browser is currently "model-free"

`scripts/copy-runtime-assets.mjs` strips the ort WASM from the browser build, and `processors/graph-indexer/index.ts` gates embedding with `EMBEDDING_ENABLED = typeof window === "undefined"`. Commit `2a4d7f02` explains why.

- **Embedding was moved into the server processor on purpose.** That gives semantic search one durable, shared vector store that works headless.
- **The ort asset is stripped only because it's unreachable.** Every call site sits behind that gate, so the ~22.8 MB file was dead weight in the tarball.

So nothing about browsers blocks a chat. Scope B would add a *second*, chat-only embedding path. The chat would load its runtime and models lazily from Hugging Face, outside the package bundle, without touching the processor's design. If Scope B uses a different embedding model, its vectors won't be interchangeable with the server's gte-small index.

## First spike (cheapest way to reduce risk)

The research left two things unverified: whether LFM2.5 actually runs in wllama, and whether wllama's `response_format: json_schema` (or GBNF) is enforced at runtime.

1. Load wllama in a worker with LFM2.5-350M Q4_K_M from Hugging Face over WebGPU, with **`n_parallel: 1`**.
2. Stream a plain chat reply. Record load time and tokens/s on WebGPU and on CPU.
3. Generate `ADD_TOPIC` (knowledge-note) input under its JSON Schema. Validate it with the Zod schema and dispatch it.
4. Hand-write 20–30 utterances across about 10 operations and measure operation selection with top-k retrieval plus constraints. This is the seed of the eval set.

## Gotchas

- **`n_parallel` must be 1.** wllama defaults it to 4, and llama.cpp #29002 reports that co-batching corrupts LFM2's recurrent state.
- **Cross-origin isolation (COOP/COEP) is only needed for multi-threaded CPU fallback**, not for WebGPU. Connect sets neither header. Adding `COOP: same-origin` breaks `window.opener` for cross-origin popups, which affects OAuth and wallet flows, so audit those first. `COEP: require-corp` blocks non-CORP subresources, so self-host wllama's compat assets. Document-Isolation-Policy avoids both problems but only works in Chromium.
- **Firefox runs at about 1 tok/s on WebGPU, and iOS tabs are capped below 500 MB.** Treat both as "best effort".
- **The model can't ship in the package bundle.** Connect loads `dist/browser` from the registry/CDN, so load the GGUF from Hugging Face or a dedicated host. `scripts/fetch-model.mjs` is an existing pattern for fetching models.
