## Format: the same as set 2

The item shape is the same as set 2:

- `id`, `style` (`natural` or `paraphrase`), `utterance`;
- `context.{docType,model,state,refCandidates}`, where each candidate is `{id,label}` and the label is human-readable;
- `expected.{op,args,ambiguousArgs,refArgs,argMatch,requiredPresent}`;
- `difficulty`, `tags`, `hardCase.{confusableWith,why}` and `notes`.

The top-level `noAction[]` entries are `{id, style, utterance, context, reason}`. The `multiAction[]` entries are `{id, style, utterance, context, expected:[step,…], orderSensitive, notes}`. Op keys are `<model>:<OP>`, where wbs is `wbs`.

The field-class rules are unchanged:

- App-filled fields never appear: new-id, timestamp/DateTime, and `actor`/`*By`.
- Ref-ids appear only in `refArgs`, and their values come from `context.refCandidates`.
- A list in `refArgs` with no `argMatch` is compared in order (`moc:REORDER_CORE_IDEAS.ids`).
- An optional semantic field that is absent from both `args` and `ambiguousArgs` should be omitted or null.

Four changes from set 2:

| change | meaning |
| --- | --- |
| Stricter paraphrase check | `validate_heldout3.py` strips one common suffix from each op-name token, as long as 4 or more letters remain (`-ation`, `-ion`, `-able`, `-ies`, `-es`, `-ed`, `-ing`, `-s`, `-e`, `-y`). It then matches the stem as a word prefix. A small derived-forms list adds `resolution`, `dissolution`, `deliver` and `refer`. So "approved", "titled", "delivered", "extracted", "dependency" and "resolution" all count as leaks. A side effect: STATS stems to `stat`, which also matches "status" and "state". That is harmless here, but a future paraphrase of RECORD_EXTRACTION_STATS must avoid those words too. A leak is an **error** on paraphrase items (including paraphrase multiAction utterances, checked against every step's op) and a warning on natural items, which gives 37 warnings, as intended. I tested this by injecting "approved", "delivered" and "resolution" into three paraphrase items: all three were rejected. The STOP list is the same as set 2's. |
| Hard assertions | The validator exits non-zero in any of these cases: the first candidate is correct more than 25% of the time; natural and paraphrase item counts differ by more than 2; there are fewer than 60 distinct ops in `items`; or not all 12 models appear. |
| `requiredPresent` | Contains the required semantic fields placed in `ambiguousArgs`. It also contains fields the reducer or the request makes necessary even though the schema marks them optional: `blockReason` for BLOCKED (wbs3-06, ma3-04#0), `role` (prj3-08), `description` (prj3-02) and `outcome` (wbs3-08) and `value` (kn3-09, where the field must be `scope`). |
| Semantic "ref" strings | `noteRef`, `childRef`, `targetRef`, `claimRef`, `promotedTo`, `ref` (tension) and `documentRef` are String-typed, so they are **semantic**, not ref-ids. For ADD_\* ops they sit in `ambiguousArgs` with `requiredPresent`. REMOVE_CHILD_MOC and REMOVE_OPEN_QUESTION match the stored string exactly, so those values sit in `args`, copied from the state. |

`context.state` is a partial snapshot that satisfies each reducer's preconditions. I checked these by hand against the reducer code:

- SUBMIT needs DRAFT.
- APPROVE and REJECT need IN_REVIEW, and APPROVE also needs `provenance.author` (mira) to differ from the actor ben.
- ARCHIVE needs CANONICAL, and RESTORE needs ARCHIVED.
- RESOLVE and DISSOLVE need OPEN.
- UNBLOCK needs BLOCKED.
- For ADVANCE_PHASE, `handoff.phase` equals the task's `currentPhase`, and `phaseOrder` is the seed from `pipeline-queue.json`.
- ADD_KNOWLEDGE_REF uses a ref that is not yet linked, and REMOVE uses one that is.
- Dependencies, parents and `insertBefore` all point at existing goals, and REORDER never moves a goal under its own subtree.
- CREATE_PROJECT, CREATE_MOC and the other CREATE\_\*/INGEST ops start from an empty state.
- No ADD duplicates an existing child MOC, topic or core idea.
- SET_DESCRIPTION is 200 characters or fewer.

Dates: **today is 2026-10-22**. So "end of next month" means `2026-11-30T00:00:00Z` (prj3-05) and "January 15" means `2027-01-15T00:00:00Z` (ma3-03), both with `argMatch: date`.

## Validation

- `python3 validate_heldout3.py` reports **0 errors and 0 assertion failures**, with 37 leak warnings, all on natural items.
- `python3 overlap_heldout3.py` finds a maximum Jaccard of 0.40 against set 2 and no shared 4-word n-gram.
- `npx --no-install tsx <scratchpad>/zodcheck3.mts`, run from the repo root, parses every expected input, with app-filled placeholders added, through the generated `<Op>InputSchema()`. That is 92 items plus 12 multiAction steps: **104/104 ok**.
- Not checked: replaying the items through the reducers. The states are partial, so I checked the preconditions above by hand.
