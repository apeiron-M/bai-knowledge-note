## Format: the same as set 3

- **Items:**
  - `id`, `style` (`natural` or `paraphrase`), `utterance`;
  - `context.{docType,model,state,refCandidates}`, where each candidate is `{id,label}`;
  - `expected.{op,args,ambiguousArgs,refArgs,argMatch,requiredPresent}`;
  - `difficulty`, `tags`, `hardCase.{confusableWith,why}` and `notes`.
- **`noAction[]`:** `{id, style, utterance, context, reason}`.
- **`multiAction[]`:** `{id, style, utterance, context, expected:[step,…], orderSensitive, notes}`.
- **Op keys:** `<model>:<OP>`, where wbs is `wbs`.
- **`conventions`:** copied from set 3, plus a `scoped` key.

The field-class rules are unchanged:

- App-filled fields never appear: new-id, DateTime, and `actor`/`*By`. That includes `publishedAt` (INGEST_SOURCE), `deliveredAt` and `handoff.id`.
- Ref-ids appear only in `refArgs`, and their values come from `context.refCandidates`. Ref-ids include `targetDocumentId`, `goalRef`, `insertBefore`, `parentId`, `wbsRef`, `projectRef` and the project's `ref` (PHID).
- Semantic String "ref" fields go in `args` or `ambiguousArgs`: `childRef`, `noteRef`, `targetRef`, `claimRef`, `promotedTo`, tension `ref` and `parentRef`. Because the user typed these values, most sit in `args` with `argMatch: ci`.
- A list in `refArgs` with no `argMatch` is compared in order (moc4-07).
- An optional semantic field that is absent from both `args` and `ambiguousArgs` should be omitted or null. Examples are `description` in prj4-02, `kind` in ma4-03, `parentId` in wbs4-05 (top level), `author` in wbs4-13, and `currentPhase` in pq4-01.
- Optional fields a model may fairly fill sit in `ambiguousArgs` but not in `requiredPresent`: `targetTitle` (kn4-09) and `rationale` (vc4-01).

Two changes from set 3:

| change | meaning |
| --- | --- |
| **Scoped** | Every item, noAction and multiAction entry carries `context.model`. The validator now checks that the model matches the op's model for every multiAction step too (set 3 skipped those). |
| **Stricter assertions** | `validate_heldout4.py` exits non-zero in any of these cases: the style split is not exactly 50/50; there are fewer than 70 distinct ops; hard items are under 25%; there are not about 100 items, 10 noAction or 6 multiAction; a hard item has no `hardCase`; a `confusableWith` entry is not a real op key or is the item's own op; or an entry is not scoped. The set-3 checks remain: the first candidate is correct at most 25% of the time, and all 12 models appear. |

**confusableWith** holds op keys only, and never the item's own op (the validator asserts this). For value-level contrasts, as in set 3 (prj3-03), it names the nearest other op and the `why` names the wrong value: prj4-03 (ON_HOLD, not ARCHIVED or COMPLETED) and prj4-04 (ARCHIVED, not COMPLETED) both point at `project:SET_DELIVERABLE_STATUS`.

**The paraphrase check** is the same stem rule as set 3. `REF` stems to `ref`, which matches "refit", "reflect" and so on. So the renovation is never called a refit in a paraphrase. A leak in a paraphrase is an error, including paraphrase multiAction utterances, which are checked against every step's op. A leak in a natural item is a warning: there are 40.

`context.state` is a partial snapshot that satisfies each reducer's preconditions. I checked these by hand against the reducer code:

- SUBMIT needs DRAFT.
- APPROVE and REJECT need IN_REVIEW, with `provenance.author` mira, not the actor ben.
- ARCHIVE needs CANONICAL, and RESTORE needs ARCHIVED.
- CREATE_PROJECT and the other CREATE/INGEST ops start from `{}`.
- RESOLVE and DISSOLVE need OPEN, and UNBLOCK needs BLOCKED.
- For ADVANCE_PHASE, `handoff.phase` equals `currentPhase` (reflect), which has successors in the seed `phaseOrder`.
- COMPLETE_TASK (pq4-05) is on a task at `verify`, the last phase.
- ADD_KNOWLEDGE_REF uses a ref that is not yet linked, and REMOVE uses one that is.
- REMOVE_OPEN_QUESTION and REMOVE_CHILD_MOC copy the stored string exactly.
- REORDER_CORE_IDEAS lists all four ids, because the reducer drops any id it is not given.
- REORDER never moves a goal under its own subtree.
- Dependencies point at existing goals, and ADD_DEPENDENCIES never adds a self-dependency.
- SET_DESCRIPTION is 200 characters or fewer.

**Dates:** today is 2026-10-22, so "the third of March" means `2027-03-03T00:00:00Z` (prj4-06, `argMatch: date`).

## Validation

- `python3 validate_heldout4.py` reports **0 errors and 0 assertion failures**. It gives 40 leak warnings, all on natural items.
- `python3 overlap_heldout4.py` compares every set-4 utterance with every set-2 and set-3 utterance (items, noAction and multiAction). The final set has a **maximum Jaccard of 0.31**: moc4-14 vs moc2-11, two version-2.1 requests in different words. **No pair shares a 4-word n-gram.** 44 pairs share a 3-word n-gram, which is reported for information only.
  - The first pass found 12 pairs above 0.40 and 30 pairs sharing a 4-word n-gram. One shared a 9-gram ("Mira's write-up checks out, sign off on it"), which shows how close independently written sets get.
  - I rewrote all of them. I then compared same-op pairs by hand and rewrote 11 more that were structural near-templates of a set-2 or set-3 item, even though they shared no 4-gram: "remove X from the team", "assign the X task to Y", "reflect is done on … pass it along", "also cite URL alongside the plan we already have", "X lives at URL now", "link this to X as builds on", "hook this up to … so its tasks show here", "jot down on X that …", "create a map called … Description … Orientation …", "archive this, …" and the reorder phrasing.
- `npx --no-install tsx <scratchpad>/zodcheck4.mts`, run from the repo root, parses every expected input through the generated `<Op>InputSchema()`, with app-filled placeholders added. That is 104 items plus 12 multiAction steps: **116/116 ok**.
- Not checked: replaying the items through the reducers. The states are partial, so I checked the preconditions above by hand.
