knowledge-vault graph-indexer processors gotchas

The processor factory creates one indexer per drive, but the reactor does not deliver operations per drive.

Mechanism

ProcessorFilter has documentType, scope, branch and documentId arrays and nothing else; OperationContext carries no drive id. So every instance is fed every drive's matching operations. Measured locally before the gate: thirteen namespaces — one per drive, twelve of them e2e leftovers — each indexing and embedding the same 594 documents.

The gate

Membership has one authoritative source and two live signals the processor already receives: the drive document's state.global.nodes, loaded once through the reactor client and reloaded (throttled) when the set looks stale; ADD_RELATIONSHIP(drive → document, "child"), the containment edge the reactor writes when a document joins a drive; and DELETE_NODE. An operation on a document outside the set is ignored.

Consequence elsewhere

The tension automation has the same problem in miniature — an instance for another vault would otherwise open a tension for this vault's contradiction and file it into the wrong drive, which was observed live — so it re-checks membership before writing.
