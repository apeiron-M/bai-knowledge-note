Where this differs from the first plan

The first plan gets the big calls right: three models, one tab, author bottom-up, report top-down, no cascades, knowledge stays on the execution project. Three things I would change.

First planThis proposalWhy
Compile unit bai/project ↔ SoW deliverable, 1:1 bai/project ↔ SoW project; deliverable ↔ top-level WBS goal Paperless has one team of 4, 10 cited notes, 7 deliverables. Project-per-deliverable means 7 projects, the roster copied 7×, knowledge scattered 7×. It also makes bai/wbs a real WBS: deliverables at the top, tasks below.
SoW model add executionRef: PHID to Deliverable leave it alone; link from the vault side powerhouse/scopeofwork is upstream (@powerhousedao/project-management 1.0.6) and the vendored copy already diverges — Progress union → flat type, marginPinned, targetBudget. Every field added here is a merge conflict later.
Nav two bands in “Projects”: execution, then scope one list grouped by SoW, + “Not in a scope” group, + Mine / My teams Several SoWs across teams and companies. Bands answer “which SoWs exist”; groups answer “whose work is this”. Grouping is already the vault's idiom (GROUP_ORDER, STATUS_ORDER).
Sequencing nav bands → schema glue → compile picker identity first, then grouping, then the one join field “Users and teams report their work” is the stated goal and it is blocked by five spellings of a person, not by the compile link.
Also worth knowing before you promise deep links. The SoW editor navigates by React state only — go(view) with a View union, no routing. Clicking a deliverable in the vault cannot open that deliverable in the SoW editor until the editor accepts an initial view. Its PlanMatrix (projects × milestones) and roadmap / milestone / project / team views already exist, so the top-down half is largely built — only Deliverable has an inspector, which is exactly where the execution chip goes.
Upstream nit. SoW uses owner: ID and coordinators: [ID!]!. The house rule in this repo's CLAUDE.md is explicit: never use ID in a document model — OID for in-document, PHID for cross-document. Worth filing against project-management rather than fixing only in the fork.
